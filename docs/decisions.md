## Markdownインポート（2026-09-28 ユーザー決定、§15 追加候補の方針転換）

自由書式の手書き Markdown（`recipe/*.md` のような日々のメモ）から、既存のレシピ登録フォームへ手入力する手間を省くため、貼り付け／ファイル選択で一括登録できる機能を実装する。人数換算・調理記録は対象外のまま。

| 論点 | 決定 | 理由 |
| --- | --- | --- |
| 解析方式 | **AI（Gemini）による正規化 → ローカルの決定的パーサ**の2段構成にする。AIに直接 `RecipeInput[]` の JSON を生成させない | 自由書式の見出し構造・単位表記のゆれは人間には自明でもAIの構造化出力だけに任せると誤分割・誤解析が検出できない。いったん人間にもレビューしやすい中間テンプレート（Markdown）に落とすことで、(1) 編集して再解析するフォールバックが自然に作れる、(2) パーサ部分を vitest で決定的にテストできる、(3) AIの出力形式が単純（`{markdown: string}`）になりAI呼び出しの失敗モードが減る |
| フォールバック | 「AIスキップ」のような別トグルは作らない。整形結果を編集可能なテキストエリアに出し、手直しして「この内容で読み込み直す」で**ローカル解析のみ**再実行できるようにする | AIが失敗/誤変換した場合の唯一の回復手段をテキストエリアの手直しに統一し、UIの分岐を増やさない |
| 正規化テンプレートの区切り文字 | 材料行を `- 名前 | 分量 | 単位 | 補足` の `|` 区切りにする | 分量・単位が「大さじ1」「100〜150g」のように自然文中で結合しているため、キーごとに区切らないと決定的に分離できない。`|` は日本語のレシピ文中にまず出現せず、`[[id|語句]]` 記法との視覚的な違いも大きいため区切り文字として採用。手順本文には `|` 分割ロジックを一切適用しないことで `[[id|語句]]` 記法と衝突しない |
| 入力口 | テキスト貼り付けと `.md` ファイル選択（複数可）の両方を用意する | 直接貼り付けたい場合と、既存の `recipe/*.md` を丸ごと読み込みたい場合の両方に対応するため |
| ファイルの整形リクエスト単位 | 複数ファイルは1件ずつ順に `/api/import-normalize` を呼ぶ | 複数日分をまとめて1リクエストにすると、AIの出力トークン上限で末尾が切れるリスクがあるため |

### 整形と分類を2パスに分けた（2026-09-28）

実機での利用で「手入力では判断できないので、カテゴリ・タグ・人数・調理時間はAIに内容から推測して必ず埋めてほしい」という要望があり、当初は下記「メタデータの自動補完」のとおり `/api/import-normalize` の1つのプロンプトに整形とメタデータ推測を同居させた。ところが本番投入後、以下の事実が判明した。

- **`/api/arrange`（AIアレンジ）は同じモデル`gemini-3.6-flash`・同じAPIキーで正常に動いていた**。
- **7行程度の1レシピでも `/api/import-normalize` が503になった**（`callGeminiWithRetry` のリトライ3回すべて即503で失敗）。
- 入力サイズの問題や Google 側の容量問題では説明が付かない（同時刻に `/api/arrange` は正常）。**取り込み側のリクエストの形が固有に弾かれていた**。
- 動いていた版（コミット `1057ef2`）のシステムプロンプトは3,788バイト。メタデータ補完（カテゴリ7種の列挙と境界ルール、調理法11種の列挙、タグの個数・構成規則、「4項目だけが例外」という書き分け）を足した結果、7,203バイトまで肥大化していた。

これらから、**1つのプロンプトに整形とメタデータ推測(分類)を詰め込んだこと自体が503の原因**と判断し、次のとおり2パスに分離した。

| パス | エンドポイント | 役割 | プロンプトサイズ |
| --- | --- | --- | --- |
| 整形 | `POST /api/import-normalize` | 自由書式Markdown→正規化テンプレート。メタデータの4行はテンプレートに残すが、**入力に書かれていればそのまま、無ければ空欄**(`1057ef2`の挙動に戻す) | 3,771バイト(目標4,500以下) |
| 分類 | `POST /api/import-classify`(新規) | 正規化済みレシピ(材料名・手順本文だけの軽い表現)からカテゴリ・タグ・人数・調理時間を推測 | 1,665バイト(目標2,500以下) |

- 統合はサーバー側では行わず、**ローカルの決定的関数**(`src/lib/recipeMetadataMerge.ts` の `applyMetadataToTemplate`)がテンプレート文字列そのものを書き換える。整形結果のテキストエリアが唯一の正であり続け、「この内容で読み込み直す」で再解析しても分類結果は消えない。
- 分類のレスポンスは構造化出力(`responseSchema`)なので、**語彙をサーバー側でコードとして機械的に強制できる**ようになった(`api/_lib/import/classify-schema.ts`)。1つのプロンプトに同居していた頃は、パーサの警告(`src/lib/recipeMarkdown.ts`)でしか語彙の逸脱に気づけなかった。
- 分類が失敗しても整形済みのレシピの取り込み自体はブロックしない(「カテゴリ・タグをもう一度判定」で分類だけ再試行できる。`src/pages/RecipeImport.tsx`)。

以下「メタデータの自動補完」節の表・語彙・個数規則は内容としては維持するが、**適用先が `/api/import-normalize` のプロンプトから `/api/import-classify` のプロンプトに移った**(2026-09-28)。

### メタデータ（カテゴリ・タグ・人数・調理時間）の自動補完（2026-09-28 追加決定。現在は `/api/import-classify` が担う）

材料・手順・分量・レシピ名の創作禁止は維持しつつ、この4項目に限って以下のとおりAIに補完させる。

| 項目 | 方針 |
| --- | --- |
| カテゴリ | **必須・1つ**。次の7種類の語彙に固定し、AIに新しい語を作らせない: `主菜` / `副菜` / `汁物` / `主食` / `丼` / `デザート` / `その他`。「その他」はどれにも当てはまらない場合だけ使う |
| タグ | **必須**。下記「タグの個数・構成」のとおり、日付が取れれば3〜4個、取れなければ3個 |
| 人数 | **必須**。元のMarkdownに書かれていればそれを優先し、無ければ材料の分量から推測する。既存データの表記（`1人分`／`2人分`／`1〜2食分`／`約4人分` 等）に倣う |
| 調理時間 | **必須**。元のMarkdownに書かれていればそれを優先し、無ければ手順から目安を**整数の分だけ**で入れる（`20`。「約20分」のような単位付き文字列にしない） |

### タグの個数・構成（2026-09-28 レビューで修正）

初版の「日付1＋主な材料1〜2＋調理法1＝3〜5個」は算数が合わなかった（日付が無い入力では材料1＋調理法1＝2個で下限3に届かず、上限も日付1＋材料2＋調理法1＝4個で5個に届かない）。個数規則を次に置き換える。

- 日付が取れる場合: 日付1個＋主な材料1〜2個＋調理法1個 = **3〜4個**
- 日付が取れない場合: 主な材料**2個**＋調理法1個 = **3個**
- 語彙外の自由なタグを足して個数を埋めない。カテゴリと同じ語をタグに入れない。

**日付タグはファイル名からも取れるようにする**: 既存41件は全件が日付タグ運用のため、本文に日付が無いファイル（`recipe/2026-09-15_recipe.md` の `# 鯖と玉ねぎ・人参の生姜醤油炒め` など、本文に日付が一切無い見出し）で日付タグが落ちるのを防ぐ。`/api/import-normalize` のリクエストに任意の `sourceName`（元ファイル名）を追加し、本文に日付が無い場合のフォールバックとしてAIに使わせる（本文の日付を優先）。貼り付けテキストのときは `sourceName` を渡さない（`src/pages/RecipeImport.tsx`）。

### 見出しパターンへの対応（2026-09-28 追加決定）

実データの見出しは「# 2026-09-20」のような日付だけの形が少数派で、以下が主流と判明した。

- `recipe/2026-09-09_recipe.md` / `2026-09-14_recipe.md` は `# 2026-09-09 晩ご飯レシピ` のような**日付＋語句**の見出し
- `recipe/2026-09-15_recipe.md` / `2026-09-17_recipe.md` は本文に日付が一切無い（`# 鯖と玉ねぎ・人参の生姜醤油炒め` / `# 今日の夕飯レシピ`）
- `recipe/2026-09-16_recipe.md` は `# 冷凍鮭のみぞれ煮献立`（献立見出し）→ `# 冷凍鮭のみぞれ煮`（実レシピ）のように、献立見出しの直後に個別レシピが続く構成

これに対応するため、プロンプトに以下を明記する（対応しないと「2026-09-09 晩ご飯レシピ」のような幽霊レシピが1件生成される）:

- 日付＋語句の見出しも献立の日付見出しとして扱い、レシピ名にしない。日付はタグに入れる。
- 「今日の夕飯レシピ」「○○献立」のようにその日の献立全体を指す見出しはレシピ名にしない。直後に個別の料理見出しが続く場合はそれぞれを独立したレシピとして出力する。

- カテゴリの語彙を7種類に固定する理由: `RecipeList` のカテゴリ絞り込み `<select>` は登録済みレシピから動的に生成されるため、AIが自由な語を作ると表記ゆれで選択肢が断片化する。既存41件は `主菜`/`副菜`/`汁物`/`主食`/`丼` の5種のみで運用しているため、原則この5種に寄せる（`デザート`/`その他` は将来の拡張・例外用）。
  - `丼`/`主食`、`主菜`/`副菜` の境界: ご飯に具を乗せる・かけるものは `丼`、それ以外の主食（パスタ・麺・パン・炊き込みご飯）は `主食`。肉・魚が主役なら `主菜`、野菜・豆腐・卵が主役の小皿なら `副菜`。
- 調理法タグを列挙に固定する理由も同様（タグは自由入力だが、少なくともAI補完分は表記ゆれを防ぐ）。この列挙が語彙の正であり、`api/_lib/import/classify-prompt.ts` と `docs/api.md` はここに書かれた語彙をそのまま使う。調理法の語彙から `汁物` は**除外する**（カテゴリの `汁物` と重複すると、味噌汁のようなレシピでタグの必須3枠の1つが実質同語反復＝情報ゼロになるため。2026-09-28 レビュー指摘）。調理法の語彙（10種）: `炒め物` / `煮物` / `煮込み` / `蒸し料理` / `焼き物` / `揚げ物` / `和え物` / `サラダ` / `レンジ` / `生`。
- 補完してよいのはこの4項目だけ。材料・手順・分量・レシピ名・`概要` は引き続き入力に書かれていることだけを書く（AIには創作させない）。整形（`/api/import-normalize`）と分類（`/api/import-classify`）を2パスに分けたことで、整形側のプロンプトは「創作しない」だけを言えばよくなり、分類側のプロンプトは「推測して埋める」だけを言えばよくなった（1つのプロンプトで両立させようとして「4項目だけが例外」と書き分けていたのが元々の無理だった。上記「整形と分類を2パスに分けた」参照）。分類側のfew-shot例が無い（`classify-prompt.ts` はJSON入出力のみで自然文の例を持たない）ため、整形側の正規化テンプレート例の本文とタグは引き続き一致させる（例に無い材料・手順をタグに出すと、指示文より強く効くfew-shot例自体が「創作しない」ルールと矛盾して見えるため。2026-09-28 レビュー指摘）。
- AIが取りこぼした場合に気づけるよう、ローカルパーサ（`src/lib/recipeMarkdown.ts`）はカテゴリが空・タグが0件のときにwarningを出す（登録はブロックしない。人数・調理時間は手直し時に空でも自然なのでwarningは出さない）。カテゴリが空でなく7種類の語彙に含まれない場合もwarningを出す（語彙固定の目的が崩れるため）。タグ側の語彙（調理法）は手直し時のノイズになるためwarningを出さない。

## その他の実装判断

- 材料・手順はレシピドキュメント内の配列として保持する（別コレクションにしない）。並び順は配列の順序で表現する。
- テクニックの `instructions` は文字列配列（1要素＝1手順）。
- Firebase Storage は使わない。
- AIアレンジを子レシピとして保存するとき、`safetyNotes` と `changeSummary` もレシピに保存する（2026-09-14 レビュー指摘で追加。data-model.md 参照）。
- 状態管理は React Context + hooks のみ。UIライブラリは使わず、モバイルファーストの素のCSSで作る。
- Gemini呼び出しのリトライ（2026-09-28、`api/_lib/ai.ts`）: `503`（モデル過負荷）と`429`（レート制限）は一時的な状態なので最大2回までリトライする。それ以外（400系・`invalid_ai_output`等）はコード側の問題やリトライしても直らない失敗なので即座にエラーを返す。詳細は docs/api.md「共通」参照。500/502/504のリトライ追加や、429の「日次クォータ超過」と「一時的レート制限」の区別は2026-09-28時点では見送り。実運用で500系が頻発するようなら追加を検討する。
