## Markdownインポート（2026-09-28 ユーザー決定、§15 追加候補の方針転換）

自由書式の手書き Markdown（`recipe/*.md` のような日々のメモ）から、既存のレシピ登録フォームへ手入力する手間を省くため、貼り付け／ファイル選択で一括登録できる機能を実装する。人数換算・調理記録は対象外のまま。

| 論点 | 決定 | 理由 |
| --- | --- | --- |
| 解析方式 | **AI（Gemini）による正規化 → ローカルの決定的パーサ**の2段構成にする。AIに直接 `RecipeInput[]` の JSON を生成させない | 自由書式の見出し構造・単位表記のゆれは人間には自明でもAIの構造化出力だけに任せると誤分割・誤解析が検出できない。いったん人間にもレビューしやすい中間テンプレート（Markdown）に落とすことで、(1) 編集して再解析するフォールバックが自然に作れる、(2) パーサ部分を vitest で決定的にテストできる、(3) AIの出力形式が単純（`{markdown: string}`）になりAI呼び出しの失敗モードが減る |
| フォールバック | 「AIスキップ」のような別トグルは作らない。整形結果を編集可能なテキストエリアに出し、手直しして「この内容で読み込み直す」で**ローカル解析のみ**再実行できるようにする | AIが失敗/誤変換した場合の唯一の回復手段をテキストエリアの手直しに統一し、UIの分岐を増やさない |
| 正規化テンプレートの区切り文字 | 材料行を `- 名前 | 分量 | 単位 | 補足` の `|` 区切りにする | 分量・単位が「大さじ1」「100〜150g」のように自然文中で結合しているため、キーごとに区切らないと決定的に分離できない。`|` は日本語のレシピ文中にまず出現せず、`[[id|語句]]` 記法との視覚的な違いも大きいため区切り文字として採用。手順本文には `|` 分割ロジックを一切適用しないことで `[[id|語句]]` 記法と衝突しない |
| 入力口 | テキスト貼り付けと `.md` ファイル選択（複数可）の両方を用意する | 直接貼り付けたい場合と、既存の `recipe/*.md` を丸ごと読み込みたい場合の両方に対応するため |
| ファイルの整形リクエスト単位 | 複数ファイルは1件ずつ順に `/api/import-normalize` を呼ぶ | 複数日分をまとめて1リクエストにすると、AIの出力トークン上限で末尾が切れるリスクがあるため |

## その他の実装判断

- 材料・手順はレシピドキュメント内の配列として保持する（別コレクションにしない）。並び順は配列の順序で表現する。
- テクニックの `instructions` は文字列配列（1要素＝1手順）。
- Firebase Storage は使わない。
- AIアレンジを子レシピとして保存するとき、`safetyNotes` と `changeSummary` もレシピに保存する（2026-09-14 レビュー指摘で追加。data-model.md 参照）。
- 状態管理は React Context + hooks のみ。UIライブラリは使わず、モバイルファーストの素のCSSで作る。
