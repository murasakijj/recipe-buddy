# レシピ料理支援Webアプリ MVP仕様書

- バージョン：0.1
- 作成日：2026-09-13
- ステータス：初期仕様／レビュー待ち
- 想定読者：プロダクトオーナー、Claude、Codex、実装担当者

## 1. 文書の目的

本書は、自分が作れる料理のレシピを蓄積し、その日の材料や状況に合わせて調整し、スマートフォンで料理を支援するWebアプリのMVP仕様を定義する。

実装時にClaudeやCodexが独自判断で機能範囲を広げないよう、以下を明確にする。

- アプリが解決する問題
- MVPに含める機能と含めない機能
- 主要な利用フロー
- 画面、データ、AI機能の基本要件
- 未決事項と将来拡張

## 2. 背景と解決したい問題

一般的な料理本やレシピは、記載された材料・分量・状態が揃っていることを前提としている。しかし実際の家庭では、材料不足、別食材への代替、冷凍状態、余っている食材の追加などが頻繁に発生する。

また、料理中にスマートフォンでレシピを確認すると、画面が自動消灯してしまい、再表示の操作が必要になる。手が濡れている、汚れている、塞がっている場面では、この操作負荷が大きい。

さらに、野菜の切り方や冷凍・解凍方法など、複数のレシピで共通する基礎手順をレシピごとに重複して記載すると、本文が長くなり、情報の更新や再利用もしづらい。

本アプリは、これらを次の構造で解決する。

1. 自分のレシピを蓄積・閲覧する
2. 元レシピを、その日の材料や状態に合わせた子レシピへ変換する
3. 料理中に見やすい表示と画面消灯抑止を提供する
4. 共通の料理知識をレシピ本文から分離し、必要なときだけ参照できるようにする

## 3. プロダクトコンセプト

> 自分のレシピを蓄積し、その日の材料や状況に合わせて「今日作れるレシピ」へ変換して、実際の調理まで支援するWebアプリ。

### 3.1 中心となる利用モデル

`Recipe（基本レシピ） → Arrange（今回用に調整） → Cook（料理する）`

これらを横断して、`Cooking Technique（共通テクニック）` を参照する。

### 3.2 設計原則

- スマートフォンでの利用を最優先する。
- 料理中の操作回数を少なくする。
- 元レシピは、AIによるアレンジで上書きしない。
- アレンジを保存する場合は、元レシピに紐づく子レシピとする。
- 共通手順はレシピ本文へ重複記載せず、独立したデータとして参照する。
- MVPでは見栄えよりも、利用フローとデータ構造の成立を優先する。
- 未決事項を実装者が独断で拡張しない。

## 4. 対象ユーザーと利用環境

### 4.1 MVPの対象ユーザー

- 主利用者1名を想定する。
- 自分で作った、または今後作れるようにしたいレシピを管理する。
- 料理経験が浅くても、必要な基礎手順をその場で確認できることを重視する。

### 4.2 主な利用端末

- スマートフォンを最優先とする。
- PCからも、レシピ登録・編集・閲覧ができるレスポンシブWebアプリとする。
- 対象ブラウザの具体的な範囲は、技術選定時に決定する。

## 5. MVPスコープ

### 5.1 MVPに含める機能

1. レシピ一覧
2. レシピ検索・簡易絞り込み
3. レシピ詳細表示
4. レシピの新規登録・編集・削除
5. 料理モード
6. 料理モード中の画面消灯抑止
7. アレンジ要求の自由入力
8. AIによる今回用アレンジレシピの生成
9. アレンジ結果の一時利用
10. アレンジ結果を子レシピとして保存
11. 親レシピと子レシピの関連表示
12. 共通テクニックの登録・編集・削除
13. レシピ手順から共通テクニックを参照
14. 共通テクニックのモーダル表示
15. データの永続化

### 5.2 MVP対象外

- 冷蔵庫・冷凍庫・日用品などの在庫管理
- 在庫データからの自動レシピ提案
- 買い物リスト
- 複数ユーザーでの共有・権限管理
- SNS機能
- 栄養計算
- カロリー計算
- 献立自動作成
- 外部レシピサイトからの自動取得
- 音声操作
- ネイティブアプリ化
- 高度な写真・動画編集

在庫管理は、将来別ドメインまたは別モジュールとして構築し、レシピアプリとデータ連携できる構造を目指す。本MVPには含めない。

## 6. 主要ユースケース

### UC-01：登録済みレシピを探す

1. ユーザーがレシピ一覧を開く。
2. レシピ名を検索、またはカテゴリ・タグで絞り込む。
3. 対象レシピを選択する。
4. レシピ詳細が表示される。

### UC-02：基本レシピをそのまま作る

1. ユーザーがレシピ詳細を開く。
2. 「料理モード」を開始する。
3. 材料と手順を見ながら調理する。
4. 分からない共通テクニックのリンクを押す。
5. モーダルで説明を確認し、閉じて同じ手順へ戻る。
6. 料理モードを終了する。

### UC-03：材料や状態に合わせてアレンジする

1. ユーザーが親となるレシピ詳細を開く。
2. 「アレンジする」を押す。
3. 現在の状況を自由入力する。
4. AIが元レシピと入力内容を基に、今回用アレンジレシピを生成する。
5. ユーザーが変更点と完成版レシピを確認する。
6. そのまま料理モードで使用する、または子レシピとして保存する。

入力例：

> 玉ねぎがない。人参ならある。豚肉は冷凍で固まっていて、1枚ずつ剥がれない。

期待する出力例：

- 玉ねぎを材料から削除する。
- 人参を代替食材として追加する。
- 火が通りやすい切り方と下準備を追加する。
- 冷凍豚肉を塊のまま加熱し、外側から剥がす手順へ変更する。
- 必要に応じて加熱時間と火加減を修正する。

### UC-04：アレンジを子レシピとして残す

1. ユーザーが生成されたアレンジを確認する。
2. 「子レシピとして保存」を押す。
3. 名前を確認・変更して保存する。
4. 親レシピとの関連を保持する。
5. 以後、通常のレシピと同様に閲覧・編集・料理モード利用ができる。

### UC-05：共通テクニックを確認する

1. 手順内のリンク表示された語句を押す。
2. ページ遷移せずモーダルが開く。
3. テクニック名、説明、手順、注意点を確認する。
4. モーダルを閉じる。
5. レシピ内の元の閲覧位置が維持される。

## 7. 機能要件

### FR-01：レシピ一覧

- 登録済みレシピを一覧表示する。
- 各項目には最低限、レシピ名を表示する。
- 画像が登録されている場合はサムネイルを表示できる。
- 親レシピと子レシピを識別できる表示を設ける。
- レシピを選択すると詳細画面へ遷移する。

### FR-02：検索・絞り込み

- レシピ名の部分一致検索ができる。
- カテゴリまたはタグによる絞り込みができる。
- MVPでは複雑な全文検索や高度な条件検索を必須としない。

### FR-03：レシピ詳細

MVPでは一般的なレシピと同様の、文字中心の箇条書き表示とする。

最低限、次を表示する。

- レシピ名
- 概要またはメモ（任意）
- 何人分か
- 調理時間（任意）
- 材料名、分量、単位、補足
- 番号付きの調理手順
- 共通テクニックへのリンク
- 親レシピまたは子レシピとの関係
- 編集、削除、料理モード、アレンジ開始の各操作

表示例：

```text
鮭のホイル焼き

材料（2人分）
- 鮭：2切れ
- 玉ねぎ：1個
- 人参：1/2本

手順
1. 玉ねぎを薄切りにする。
2. 人参を［細切り］にする。
3. アルミホイルに材料を載せる。
4. フライパンで蒸し焼きにする。
```

`［細切り］` は共通テクニックへの参照であり、押すとモーダルを開く。

### FR-04：レシピ登録・編集

- レシピを新規登録できる。
- 登録済みレシピを編集できる。
- 材料は複数行追加でき、並び替えできる。
- 手順は複数行追加でき、番号順に並び替えできる。
- 各手順の任意の語句へ、1件以上の共通テクニックを紐づけられる。
- カテゴリ、タグ、画像は任意項目とする。
- 入力必須項目が不足している場合は、保存せず分かりやすく通知する。

### FR-05：レシピ削除

- 誤操作防止の確認を経て削除できる。
- 子レシピが存在する親レシピを削除する場合、影響を表示する。
- 親削除時の子レシピの扱いは、未決事項として実装前に確定する。

### FR-06：料理モード

- レシピ詳細から開始できる。
- 材料と手順をスマートフォンで読みやすい大きさ・余白で表示する。
- 編集や削除など、料理中に不要な操作を隠す。
- 共通テクニックのモーダルを利用できる。
- 明示的に終了できる。
- アレンジレシピにも利用できる。

### FR-07：画面消灯抑止

- 料理モード開始時、対応環境では Screen Wake Lock API等を使用し、画面の自動消灯を抑止する。
- 料理モード終了時は、取得したWake Lockを解放する。
- ブラウザの仕様や端末設定により抑止できない場合、料理モード自体は継続して利用できる。
- 抑止に失敗した場合は、ユーザーへ簡潔に状態を知らせる。
- タブの非表示、画面ロック、アプリ切り替えなどでWake Lockが解除された場合、画面復帰時に可能なら再取得する。
- 対象となる実機・ブラウザで動作検証を行う。

### FR-08：アレンジ入力

- レシピ詳細から開始する。
- 自由記述欄を設ける。
- ユーザーは、材料不足、代替希望、材料の状態、追加したい材料、分量、調理器具、時間などを自然文で入力できる。
- 生成開始前に、対象となる元レシピを画面上で確認できる。

### FR-09：AIによるアレンジ生成

- AIへ元レシピ全体とユーザーの要求を渡す。
- 単なる代替候補ではなく、完成した今回用レシピを生成する。
- 材料、分量、下準備、手順、火加減、加熱時間、注意点を必要に応じて整合させる。
- 変更不要な部分は可能な限り元レシピを維持する。
- 元レシピのデータを上書きしない。
- 不足情報が安全性や完成可能性へ大きく影響する場合は、断定せず追加確認を求める。
- 生焼け、加熱不足など食品安全上のリスクがある場合は注意を明示する。
- 生成失敗時は元レシピを保持し、再試行できる。

### FR-10：アレンジ結果

- 元レシピからの主な変更点を表示する。
- 変更後の材料一覧と調理手順を、通常の詳細画面と同じ形式で表示する。
- 「今回だけ使う」「子レシピとして保存」「入力を修正して再生成」を選べる。
- 保存前でも料理モードへ移行できる。

### FR-11：親レシピ・子レシピ

- 保存されたアレンジは、元レシピの子レシピとして保持する。
- 子レシピは通常のレシピと同じ情報構造を持つ。
- 子レシピから親レシピを参照できる。
- 親レシピから子レシピ一覧を参照できる。
- 子レシピを編集しても親レシピは変更しない。
- MVPでは親子関係を1階層に限定するか、子からさらに派生可能にするかは未決事項とする。

### FR-12：共通テクニック管理

- 共通テクニックを独立して登録・編集・削除できる。
- 最低限、名称、説明、手順、注意点を保持する。
- 画像や動画は将来追加できる構造を考慮するが、MVP必須ではない。
- 例：細切り、みじん切り、乱切り、ほうれん草の下茹で、ひき肉の小分け冷凍、冷蔵庫解凍、蒸し焼き、味噌を溶くタイミング。

### FR-13：共通テクニック参照・モーダル

- レシピ本文へURL文字列を直接埋め込まず、テクニックIDによる参照関係を保持する。
- 手順内では、紐づけられた語句をWebリンクに似た見た目で表示する。
- 押下時にページ遷移せずモーダルを開く。
- モーダルを閉じた際、元のレシピとスクロール位置を維持する。
- 同じ共通テクニックを複数レシピから参照できる。
- 共通テクニックの内容を更新した場合、参照元では更新後の内容を表示する。

## 10. データモデル（論理仕様）

技術スタックやDB製品には依存しない。ID、作成日時、更新日時などの一般的な管理項目は各エンティティに持たせる。

### 10.1 Recipe

| 項目 | 必須 | 説明 |
| --- | --- | --- |
| id | 必須 | レシピ識別子 |
| title | 必須 | レシピ名 |
| description | 任意 | 概要・メモ |
| servings | 任意 | 基準人数 |
| cooking_time_minutes | 任意 | 調理時間 |
| parent_recipe_id | 任意 | 子レシピの場合の親レシピID |
| source_type | 必須 | manual / ai_arranged 等 |
| arrangement_request | 任意 | 子レシピ生成時のユーザー要求 |
| category | 任意 | カテゴリ |
| image | 任意 | 代表画像の参照 |
| created_at | 必須 | 作成日時 |
| updated_at | 必須 | 更新日時 |

### 10.2 RecipeIngredient

| 項目 | 必須 | 説明 |
| --- | --- | --- |
| id | 必須 | 材料行識別子 |
| recipe_id | 必須 | 所属レシピID |
| name | 必須 | 材料名 |
| quantity | 任意 | 分量。1/2などを扱えること |
| unit | 任意 | g、ml、個、切れ、適量など |
| note | 任意 | 冷凍、薄切り等の補足 |

将来の在庫連携に備え、表示名とは別に食材マスタIDを持てる余地を残す。ただし食材マスタの本格実装はMVP必須ではない。

### 10.3 RecipeStep

| 項目 | 必須 | 説明 |
| --- | --- | --- |
| id | 必須 | 手順識別子 |
| recipe_id | 必須 | 所属レシピID |
| instruction | 必須 | 手順本文 |
| sort_order | 必須 | 手順番号・表示順 |

### 10.4 Technique

| 項目 | 必須 | 説明 |

| id | 必須 | テクニック識別子 |
| name | 必須 | 名称 |
| summary | 任意 | 短い説明 |
| instructions | 必須 | 詳細手順 |
| cautions | 任意 | 注意点 |
| media | 任意 | 画像・動画の参照 |
| created_at | 必須 | 作成日時 |
| updated_at | 必須 | 更新日時 |

### 10.5 RecipeStepTechnique

| 項目 | 必須 | 説明 |
| --- | --- | --- |
| id | 必須 | 関連識別子 |
| recipe_step_id | 必須 | 対象手順ID |
| technique_id | 必須 | 共通テクニックID |
| display_text | 必須 | リンクとして表示する語句 |
| position情報 | 要検討 | 本文中の該当位置。実装方式に応じて決定 |

### 10.6 Tag / RecipeTag

タグ絞り込みを実装する場合に使用する。MVPでは文字列配列として簡略化する選択も可。ただし将来の表記揺れ対策を考えると、独立マスタが望ましい。

### 10.7 一時アレンジデータ

保存前のアレンジ結果は、必ずしも永続化を必要としない。再読み込み後も残すか、セッション中のみとするかは技術設計時に決定する。保存操作を行った場合はRecipeとして永続化する。

## 11. AIアレンジ機能仕様

### 11.1 AIへの入力

- 元レシピの基本情報
- 元レシピの材料一覧
- 元レシピの手順一覧
- 手順に紐づく共通テクニックID・名称
- ユーザーの自由記述によるアレンジ要求
- 必要に応じて人数などの条件

### 11.2 AIに求める出力

AIの応答は、画面表示用の文章だけでなく、アプリが検証・保存可能な構造化データとする。

最低限、次を返す。

- アレンジレシピ名
- 変更点の要約
- 変更後の材料一覧
- 変更後の手順一覧
- 既存の共通テクニックへの参照候補
- 安全上の注意
- 確認が必要な事項（ある場合）

### 11.3 AI出力ルール

- 元レシピを破壊・更新しない。
- ユーザーの要求を優先しつつ、料理として成立するよう全体を調整する。
- 食材を置換した場合は、切り方、下処理、投入順、加熱時間などの影響も反映する。
- 冷凍・解凍状態などが変わる場合は、必要な前処理と安全上の注意を反映する。
- 実在しない共通テクニックIDを生成しない。
- 既存テクニックに該当しない説明は通常の手順として出力し、新規Technique候補として区別して返してもよい。
- 数値や単位は、可能な限り構造化して返す。
- AI出力は必ずサーバー側またはアプリ側でスキーマ検証してから表示・保存する。

### 11.4 AI障害時

- タイムアウト、通信失敗、形式不正を区別せずとも、ユーザーに再試行可能なエラーを表示する。
- 入力した要求を失わない。
- 元レシピに影響を与えない。
- 不完全な生成結果を自動保存しない。

## 12. 非機能要件

### 12.1 ユーザビリティ

- スマートフォンの片手操作を考慮する。
- 主要操作は明確なラベル付きボタンとする。
- 料理モードでは文字サイズと行間を十分に確保する。
- 誤ってモーダル外を触れても、必要以上に状態を失わない。
- 削除など破壊的操作には確認を設ける。

### 12.2 性能

- 通常の一覧・詳細表示は、家庭内の一般的な通信環境で待ち時間を意識しにくい速度を目指す。
- AI生成中は処理中であることを明示し、二重送信を防ぐ。
- レシピ件数の初期想定は小規模だが、数百件程度で基本操作が著しく劣化しない構造とする。

### 12.3 可用性・データ保護

- 保存済みレシピと共通テクニックを永続化する。
- AI生成失敗で元データを破損しない。
- 編集保存の失敗時に入力内容を可能な限り保持する。
- バックアップ・エクスポート方式は実装前に検討する。

### 12.4 セキュリティ

- AIサービスのAPIキーをブラウザへ直接露出しない。
- 外部入力およびAI出力を信頼せず、保存・表示前に検証する。
- レシピ本文等を表示する際は、スクリプト注入を防止する。
- 認証の要否は未決事項。外部公開する場合は、個人データの編集画面を第三者が操作できないようにする。

### 12.5 アクセシビリティ

- リンク、ボタン、通常テキストを色だけで区別しない。
- タップ領域を十分に確保する。
- キーボード操作でも主要画面とモーダルを利用できる構造を目指す。
- モーダル表示中のフォーカス制御と、閉じた後のフォーカス復帰を考慮する。

## 13. MVP受入条件

以下をすべて満たした場合、MVPの主要目的を達成したと判断する。

1. スマートフォンからレシピを登録・編集・削除できる。
2. 一覧から検索し、材料と手順を含む詳細を表示できる。
3. 詳細から料理モードを開始できる。
4. 対応環境では料理モード中の画面自動消灯を抑止できる。
5. 画面消灯抑止が利用できない場合も、レシピ閲覧は継続できる。
6. 手順内の共通テクニックリンクからモーダルを開閉できる。
7. モーダルを閉じた後、レシピの閲覧位置が維持される。
8. 元レシピと自然文の要求から、材料・前処理・手順・加熱条件を整合させたアレンジレシピを生成できる。
9. 生成したアレンジを保存せず料理に使える。
10. 生成したアレンジを親レシピに紐づく子レシピとして保存できる。
11. 親と子を相互にたどれる。
12. アレンジ生成や保存に失敗しても、元レシピが変更・破損しない。

## 14. 実装前に決める未決事項

優先度Aは、実装開始前または該当機能の着手前に決める。優先度Bは、仮置きで進めることも可能。

| 優先度 | 未決事項 | 主な選択肢・論点 |
| --- | --- | --- |
| A | 利用者と認証 | 本人のみ／家族共有、ログイン必須か |
| A | 配置・公開範囲 | ローカル、家庭内、インターネット公開、非公開ホスティング |
| A | AIサービス | 使用モデル、API、費用上限、応答速度 |
| A | AI確認フロー | 情報不足時に質問を返すか、注意付きで生成するか |
| A | 親子階層 | 1階層のみ／子からさらに派生可能 |
| A | 親削除時の子 | 削除禁止、子も削除、子を独立化 |
| A | Technique本文内位置 | 文字位置で保持、構造化テキスト、独自記法等 |
| B | カテゴリ・タグ | 両方必要か、タグのみか |
| B | 画像 | MVPで登録必須か、任意対応か |
| B | 一時アレンジの保持期間 | セッションのみ、下書き保存 |
| B | データのバックアップ | JSON／Markdown等のエクスポート、DBバックアップ |
| B | 対応ブラウザ | 実際に料理で使うスマートフォンを基準に確定 |
| B | レシピ名の重複 | 許可するか、警告するか |

## 18. 現時点の要約

本MVPの中心価値は、単なるレシピ保管ではない。

- 基本レシピを持つ。
- 現実の材料・状態に合わせて、AIが実行可能な今回用レシピへ調整する。
- 良かったアレンジは、親に紐づく子レシピとして蓄積する。
- 切り方や下処理などの共通知識は分離し、必要な箇所からモーダルで確認する。
- 料理中は、見やすい画面と画面消灯抑止によって操作負荷を減らす。

この構造により、「自分用の料理本」ではなく、経験とアレンジを蓄積する個人向け料理支援システムを目指す。
